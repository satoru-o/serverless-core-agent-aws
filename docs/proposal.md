# 企画書:サーバーレス基幹システム + エージェント安全運用ダオ

## 1. 背景・課題

クラウド上でAIエージェントを動かすこと自体は、Lambda + Bedrock/Anthropic APIで数十行のコードで実現できる。しかし実務・学習の両面で本当に難しいのは「タスクを解かせること」ではなく、**そのエージェントを安全に、無人で、継続的に本番稼働させ続けること**である。

一方で、エージェントに「操る対象」がなければ安全設計そのものも宙に浮いてしまう。そこで本企画は2フェーズに分ける。

- **Phase 1**:エージェントが操作する対象として、サーバーレスの基幹システム(タスク管理)を作る
- **Phase 2**:そのシステムを安全に操作・監視するエージェント基盤を、権限制御・暴走防止・監査・人間承認の4本柱で段階的に構築する

学習環境には現時点で何もリソースが存在しないため、ゼロからTerraformで環境を組み立てる。RDS・EC2・Auroraのような「起動しているだけで最低ラインの課金が発生するサービス」は使用しない(Aurora Serverless v2でも最小構成で月額約6,600円が常時発生するため除外)。

## 2. 全体構成

```
【Phase 2:エージェント基盤層】(操る側)
  Lambda + Bedrock/Anthropic API
  → チケットの状況を判断し、対応・エスカレーション・完了処理を行う
  → 権限制御・暴走防止・監査・人間承認の安全設計を適用

           │ API呼び出し
           ▼

【Phase 1:サーバーレス基幹システム層】(操られる側)
  API Gateway → Lambda → DynamoDB
  → チケットの発行・対応・完了という業務ロジック
  → Step Functionsで状態遷移を管理
```

## 3. Phase 1:サーバーレス基幹システム(タスク管理)

### 3.1 業務ドメイン

チケット発行 → 対応中 → 完了、というシンプルな状態遷移を持つタスク管理システム。基幹システムとしての骨格(データの整合性、状態遷移、監査証跡)を学ぶことが目的であり、業務ドメイン自体の複雑さは最小限に留める。

### 3.2 状態遷移

```
[発行 (OPEN)] → [対応中 (IN_PROGRESS)] → [完了 (DONE)]
                        │
                        └─→ [差し戻し (REJECTED)] → [発行 (OPEN)]
```

### 3.3 システム構成

| レイヤー | 役割 | 想定サービス |
|---|---|---|
| API | チケットのCRUD操作を受け付ける | API Gateway |
| 業務ロジック | チケット作成・状態遷移・バリデーション | Lambda |
| データストア | チケット本体・履歴の永続化 | DynamoDB(シングルテーブル設計) |
| 状態遷移管理 | 発行→対応→完了のワークフロー制御 | Step Functions |
| 非同期通知 | 状態変化の通知(担当者アサイン時など) | SQS + Lambda |
| 監査ログ | 誰が・いつ・何を変更したかの記録 | DynamoDB Streams + CloudWatch Logs |
| IaC | 環境のコード化・再現性確保 | Terraform |

### 3.4 DynamoDBテーブル設計(概略)

シングルテーブル設計で、チケット本体と履歴を同一テーブルに格納する。

```
PK: TICKET#<ticket_id>       SK: METADATA           → チケット本体(状態・担当者・作成日時等)
PK: TICKET#<ticket_id>       SK: HISTORY#<timestamp> → 状態変更履歴(誰が・いつ・何を変えたか)
```

### 3.5 Phase 1の完了条件

- API経由でチケットの作成・一覧取得・状態変更ができる
- 状態遷移が定義されたルール通りにしか起こらない(例:完了済みチケットは直接「発行」に戻せない)
- 全ての状態変更が履歴として記録され、後から追跡できる

## 4. Phase 2:エージェント安全運用ダオ

### 4.1 コンセプト

Phase 1のタスク管理システムを操作対象として、エージェントに「チケットを確認し、対応し、完了させる」役割を持たせる。ただし、いきなり安全設計を全部入りにするのではなく、危険な状態を実際に体感してから対策を1つずつ追加していく。

### 4.2 学習する4つの安全設計の柱

| 柱 | 目的 | 対応する仕組み |
|---|---|---|
| ① 権限制御 | エージェントに必要最小限の権限しか与えない | IAMロール(タスク別・API限定) |
| ② 暴走防止 | 無限ループ・API連発・コスト暴走を止める | 実行回数上限、AWS Budgets + SNS、タイムアウト |
| ③ 検証・監査 | 何をしたか全て記録し、後から検証可能にする | CloudTrail、CloudWatch Logs |
| ④ 人間の承認 | 重大な操作(完了・差し戻し等)は自動実行せず人間の承認を挟む | Step Functions(waitForTaskToken)、SNS/Slack通知 |

### 4.3 進め方(段階的構築)

```
Step 0: 素朴なエージェントを作る
  → 権限は広め・承認なし・ログもほぼ無い状態で、チケットを自動処理させてみる
  → 「これはこのままでは怖い」という感覚を実際に得る

Step 1: ① 権限制御を適用する
  → IAMロールをタスクに必要な範囲(特定APIのみ呼び出し可)まで絞り込む

Step 2: ② 暴走防止を追加する
  → 実行回数上限・タイムアウトを設定
  → AWS Budgetsと連動し、予算超過で自動的にエージェントを止める仕組みを作る

Step 3: ③ 検証・監査を追加する
  → CloudTrail + CloudWatch Logsで全操作を記録
  → 「先週このエージェントが何をしたか」を後から追跡できることを確認する

Step 4: ④ 人間の承認フローを組み込む
  → 「チケットの内容を確認・提案する」は自動、「実際に完了にする」は人間承認を必須にする
  → Step Functionsで承認待ちのワークフローを構築する
```

### 4.4 システム構成

| レイヤー | 役割 | 想定サービス |
|---|---|---|
| トリガー | 定期実行・チケット作成イベント検知 | EventBridge |
| エージェント本体 | チケット内容の判断・対応方針の決定 | Lambda + Anthropic API または Bedrock |
| 権限 | 最小権限のロール分離 | IAM(タスク別ロール) |
| 予算監視 | コスト暴走の検知・自動停止 | AWS Budgets + SNS + Lambda |
| 監査ログ | 全操作の記録 | CloudTrail + CloudWatch Logs |
| 承認フロー | 重大操作の人間承認 | Step Functions + SNS(メール/Slack) |
| IaC | 全構成のコード化・再現性確保 | Terraform |
| CI/CD | デプロイの自動化 | GitHub Actions |

## 5. コスト方針

- RDS・EC2・Auroraは一切使用しない(常時課金の温床となるため)
- DynamoDBはオンデマンドキャパシティモードを使用(無料枠:月25GB、読み書き一定量まで無料)
- Lambdaは無料枠(月100万リクエスト)内での運用を想定
- Step Functionsも無料枠(月4,000ステート遷移)内での運用を想定
- Bedrock/Anthropic API呼び出しは軽量モデル(Haiku等)を優先し、1回あたりのコストを最小限に抑える
- AWS Budgetsを最初から導入し、想定外の課金が発生した場合は即座に検知・停止できる状態を保つ

## 6. 期待される効果

- 「RDB前提」から離れ、DynamoDB・Step Functionsを軸にした基幹システムの設計思想を体得できる
- タスクの複雑さに惑わされず、「エージェントを安全に運用する」という本質的な設計力が身につく
- IAM・CloudTrail・Step Functions・AWS Budgetsといった、実務でも頻出するAWSサービスへの理解が横断的に深まる
- Phase 1(操作対象)とPhase 2(操作する側)が揃うことで、安全設計の各対策を「実際の業務システムに対して」試すことができ、抽象論で終わらない

## 7. 次のステップ

1. Phase 1:タスク管理システムのDynamoDBテーブル設計・API仕様を固める
2. Phase 1:Terraformで環境を構築し、状態遷移が正しく動くことを確認する
3. Phase 2:Step 0(素朴なエージェント)を動かし、Phase 1のシステムに対して危険な挙動を実際に確認する
4. Phase 2:Step 1〜4を1つずつ、Terraformの差分として積み上げていく
5. 各Stepの完了時に振り返りを記録として残す(将来のZenn記事のネタにもなる)
