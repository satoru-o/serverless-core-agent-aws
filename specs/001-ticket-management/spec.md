# Feature Specification: チケット管理基幹システム

**Feature Branch**: `001-ticket-management`

**Created**: 2026-09-09

**Status**: Draft

**Input**: User description: "タスク管理システムを構築する。チケットを発行・対応・完了というシンプルな状態遷移で管理する、サーバーレスの基幹システム。要件: チケットの作成(タイトル・説明・担当者を指定)、チケット一覧の取得(状態でフィルタ可能)、チケット単体の取得(IDを指定)、チケットの状態変更(発行→対応中→完了、対応中→差し戻し→発行)、定義されていない状態遷移はエラーとして拒否する、全ての状態変更を履歴として記録し後から追跡できる。このシステムは後続フェーズで構築するエージェントが操作する対象となるためAPI経由での操作を前提とし、認証・権限周りは最小限でよい。スコープ外: ユーザー管理・認証機能そのものの実装、通知機能、UI、Step Functionsによる状態遷移管理"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - チケットを作成する (Priority: P1)

システムの利用者(将来的には人・エージェントの双方)が、タイトル・説明・担当者を指定して新しいチケットを起票する。作成されたチケットは「発行」状態で登録される。

**Why this priority**: チケットが作成できなければ、このシステムの他のあらゆる機能(一覧取得・状態変更・履歴追跡)が成立しない。すべての機能の土台となる最優先の能力。

**Independent Test**: タイトル・説明・担当者を指定してチケット作成APIを呼び出し、一意なIDと「発行」状態を持つチケットが生成されることを確認するだけで、単独で価値を検証できる。

**Acceptance Scenarios**:

1. **Given** システムが起動している状態、**When** タイトル・説明・担当者を指定してチケット作成を要求する、**Then** 一意なIDが採番され、状態が「発行」のチケットが新規作成される
2. **Given** 必須項目(タイトルまたは担当者)が欠落している、**When** チケット作成を要求する、**Then** チケットは作成されず、入力エラーが返される

---

### User Story 2 - チケットの状態を遷移させる (Priority: P1)

チケットの状態を「発行→対応中」「対応中→完了」「対応中→差し戻し→発行」という定義済みの流れで変更する。定義されていない遷移(例: 完了から発行への直接変更)は拒否される。

**Why this priority**: 状態遷移こそがこのシステムの中核機能であり、チケットのライフサイクル管理の目的そのもの。不正な遷移を拒否できることは、後続フェーズでエージェントがこのシステムを操作する際の安全性の土台にもなる。

**Independent Test**: 作成済みのチケットに対して定義済みの遷移(発行→対応中、対応中→完了、対応中→発行)をそれぞれ実行し状態が正しく変わることを確認する。加えて未定義の遷移(例: 完了→発行)を試み、エラーとなり状態が変化しないことを確認する。これだけで単独に価値を検証できる。

**Acceptance Scenarios**:

1. **Given** 状態が「発行」のチケットが存在する、**When** 「対応中」への状態変更を要求する、**Then** チケットの状態が「対応中」に変わる
2. **Given** 状態が「対応中」のチケットが存在する、**When** 「完了」への状態変更を要求する、**Then** チケットの状態が「完了」に変わる
3. **Given** 状態が「対応中」のチケットが存在する、**When** 「発行」への差し戻しを要求する、**Then** チケットの状態が「発行」に戻る
4. **Given** 状態が「完了」のチケットが存在する、**When** 「発行」への直接変更を要求する(定義されていない遷移)、**Then** 変更は拒否され、エラーが返され、チケットの状態は「完了」のまま変化しない
5. **Given** 状態が「発行」のチケットが存在する、**When** 「完了」への直接変更を要求する(定義されていない遷移)、**Then** 変更は拒否され、エラーが返される

---

### User Story 3 - チケット一覧を取得する (Priority: P2)

利用者が登録済みのチケットの一覧を取得する。状態(発行・対応中・完了)を指定して絞り込むこともできる。

**Why this priority**: 個々のチケットを作成・変更できても、全体像を俯瞰できなければ運用が回らない。単体取得より先に、まず「今何件、どんな状態のチケットがあるか」を把握できることが運用上重要なためP2とする。

**Independent Test**: 複数のチケットを異なる状態で作成した後、一覧取得APIを状態フィルタなし/ありでそれぞれ呼び出し、期待通りの件数・内容が返ることを確認するだけで、単独で価値を検証できる。

**Acceptance Scenarios**:

1. **Given** 複数の状態のチケットが登録されている、**When** フィルタなしで一覧取得を要求する、**Then** 登録されている全チケットが返される
2. **Given** 複数の状態のチケットが登録されている、**When** 特定の状態(例: 「対応中」)を指定して一覧取得を要求する、**Then** その状態のチケットのみが返される
3. **Given** チケットが1件も登録されていない、**When** 一覧取得を要求する、**Then** 空の一覧が正常に返される

---

### User Story 4 - チケット単体を取得する (Priority: P2)

利用者がIDを指定して、特定のチケットの詳細(タイトル・説明・担当者・現在の状態など)を取得する。

**Why this priority**: 一覧取得と対になる基本的な参照機能。個別チケットの詳細確認や、状態変更前の現状確認に必要なためP2とする。

**Independent Test**: 作成済みのチケットのIDを指定して単体取得APIを呼び出し、作成時に指定した内容と現在の状態が正しく返ることを確認するだけで、単独で価値を検証できる。

**Acceptance Scenarios**:

1. **Given** IDが判明している登録済みチケットが存在する、**When** そのIDを指定して単体取得を要求する、**Then** そのチケットの詳細情報が返される
2. **Given** 存在しないIDを指定する、**When** 単体取得を要求する、**Then** 該当チケットが存在しない旨のエラーが返される

---

### User Story 5 - 状態変更履歴を追跡する (Priority: P3)

チケットに対して行われたすべての状態変更が履歴として記録され、後からいつ・どの状態からどの状態へ変更されたかを追跡できる。

**Why this priority**: 運用上の監査・トラブルシューティングや、後続フェーズでエージェントの操作を検証する際の基盤となるが、チケット管理の基本サイクル(作成・遷移・参照)が成立した後に価値を発揮する機能のためP3とする。

**Independent Test**: あるチケットに対して複数回の状態変更を行った後、そのチケットの履歴を取得し、変更前状態・変更後状態・変更日時が変更順に正しく記録されていることを確認するだけで、単独で価値を検証できる。

**Acceptance Scenarios**:

1. **Given** 状態変更が一度も行われていない新規チケット、**When** そのチケットの履歴を確認する、**Then** 作成時点の記録(初期状態「発行」)が確認できる
2. **Given** 複数回状態変更されたチケットが存在する、**When** そのチケットの履歴を取得する、**Then** すべての変更が発生順に、変更前状態・変更後状態・変更日時とともに記録されている
3. **Given** 定義されていない遷移が拒否された(状態が変化しなかった)、**When** そのチケットの履歴を確認する、**Then** 拒否された試みは状態変更として記録されない(実際に成立した状態変更のみが記録される)

---

### Edge Cases

- 存在しないチケットIDを指定して状態変更や単体取得を要求した場合、システムは「該当なし」のエラーを返す
- 定義されていない状態遷移(例: 発行→完了への直接変更、完了→対応中への差し戻し)は拒否され、チケットの状態は変更前のまま維持される
- チケット作成時にタイトルまたは担当者が未指定・空文字の場合、作成は拒否され入力エラーが返される
- 一覧取得時に存在しない状態名でフィルタを指定した場合、入力エラーとして拒否される
- チケットが1件も存在しない状態での一覧取得は、エラーではなく空の一覧として正常に返される
- 同一チケットに対して短時間に複数の状態変更要求が競合した場合でも、履歴には実際に成立した変更のみが順序通りに記録される

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、タイトル・説明・担当者(文字列)を指定してチケットを新規作成できなければならない
- **FR-002**: システムは、作成されたチケットに一意な識別子(ID)を自動採番しなければならない
- **FR-003**: システムは、新規作成されたチケットの初期状態を「発行」としなければならない
- **FR-004**: システムは、タイトルまたは担当者が未指定・空である場合、チケット作成を拒否し、入力エラーを返さなければならない
- **FR-005**: システムは、登録済みチケットの一覧を取得できなければならない
- **FR-006**: システムは、チケット一覧取得時に状態(発行・対応中・完了)による絞り込みができなければならない
- **FR-007**: システムは、存在しない状態名でのフィルタ指定を入力エラーとして拒否しなければならない
- **FR-008**: システムは、IDを指定して特定のチケット単体の詳細を取得できなければならない
- **FR-009**: システムは、存在しないIDが指定された場合、該当チケットが存在しない旨のエラーを返さなければならない
- **FR-010**: システムは、チケットの状態変更操作を提供しなければならない
- **FR-011**: システムは、次の状態遷移のみを正当な遷移として許可しなければならない: 「発行→対応中」「対応中→完了」「対応中→発行(差し戻し)」
- **FR-012**: システムは、上記以外のあらゆる状態遷移の要求(例: 完了→発行、発行→完了、完了→対応中)をエラーとして拒否し、チケットの状態を変更してはならない
- **FR-013**: システムは、チケットに対して実際に成立したすべての状態変更を、変更前状態・変更後状態・変更日時を含む履歴として記録しなければならない
- **FR-014**: システムは、記録した状態変更履歴を後から参照・追跡できる手段を提供しなければならない
- **FR-015**: システムは、拒否された(不正な)状態遷移の試みを、成立した状態変更として履歴に記録してはならない
- **FR-016**: システムは、すべての操作(作成・一覧取得・単体取得・状態変更・履歴取得)をAPI経由で提供しなければならない
- **FR-017**: システムは、担当者を実在するユーザーとして検証せず、自由入力の文字列としてそのまま保持しなければならない

### Key Entities

- **チケット (Ticket)**: 管理対象の作業単位。ID、タイトル、説明、担当者(文字列)、現在の状態(発行・対応中・完了のいずれか)、作成日時、更新日時を持つ
- **状態変更履歴 (Status Change History)**: チケットに対して実際に成立した状態変更の記録。対象チケットのID、変更前の状態、変更後の状態、変更日時を持つ。1つのチケットは複数の履歴レコードを持ちうる

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: チケット作成の直後に一覧取得・単体取得を行った場合、100%の確率で作成したチケットの内容(タイトル・説明・担当者・状態「発行」)を確認できる
- **SC-002**: 定義されていない状態遷移の試みは、例外なく100%拒否され、対象チケットの状態は一切変化しない
- **SC-003**: 実際に成立したすべての状態変更は100%履歴に記録され、後から任意のチケットについて変更の経緯(いつ・どの状態からどの状態へ)を完全に再現できる
- **SC-004**: 利用者(人・エージェントを問わず)は、UIを一切使わずAPI呼び出しのみで、チケットの作成から状態遷移・完了までの一連の操作を完結できる
- **SC-005**: 存在しないチケットIDや不正な状態フィルタなど誤った入力を伴う要求に対して、システムは常に分かりやすいエラー応答を返し、内部エラーで処理が不定に終わることがない

## Assumptions

- 担当者(assignee)はユーザー管理・認証システムと連携しない自由記述の文字列として保持する(スコープ外要件に基づく)
- チケットの説明(description)は登録時に指定するが、必須項目とはせず空でも作成を許可する。必須項目はタイトルと担当者とする
- 状態変更履歴の閲覧はチケット単位でAPI経由により提供する(誰がいつどの状態からどの状態に変更したかを追跡する目的のため)
- 状態変更操作の呼び出し元の認証・認可(誰が変更したか)は本フェーズでは検証・記録しない。Phase 2で安全設計を段階的に追加する前提のため、現時点では操作の実行自体を最小限の制約で許可する
- 通知機能(SQS等による非同期通知)は将来拡張とし、本フェーズには含めない
- UIは提供せず、すべての操作はAPI呼び出しのみを前提とする
- 状態遷移のバリデーションはアプリケーションロジック内で行い、Step Functionsなどのワークフロー管理サービスは用いない
- 同時に複数の状態変更要求が競合した場合、後勝ちのクライアント自動リトライや分散ロックといった高度な排他制御は本フェーズの対象外とする。ただし、書き込み時点の実際の状態が前提と異なる場合は必ず変更を失敗させ(FR-012遵守)、競合した要求には通常の未定義遷移と同様のエラーを返す(この基本的な整合性担保はスコープに含む)
