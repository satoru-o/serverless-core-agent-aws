# Feature Specification: チケット管理エージェントの安全運用基盤

**Feature Branch**: `002-agent-safe-operation`

**Created**: 2026-09-14

**Status**: Draft

**Input**: User description: "チケット管理基幹システム(001-ticket-management、API: POST/GET/PATCH /tickets 等)を操作するAIエージェントを構築する。実運用中のAWSアカウントでコスト・セキュリティ両面の実害が生じうるため、無防備な状態を経験してから直す進め方は取らず、最初から安全設計を備えた状態で構築する。P1として、エージェントのIAMロールをタスクに必要な最小範囲(特定のチケットAPI呼び出しのみを許可)に絞り込んだ上で、実行回数上限・タイムアウトを設定し、AWS Budgetsと連動して予算超過時に自動的にエージェントを停止する仕組みとあわせて、初回リリース時点から組み込む。P2で、CloudTrailとCloudWatch Logsにより全操作を記録し、「先週このエージェントが何をしたか」を後から追跡できるようにする。P3で、チケットを「完了」にするなど重大な操作は自動実行せず、Step Functionsのwait-for-task-tokenパターンとSNS/Slack通知による人間承認を必須にする。スコープ外: Phase1システムの業務ロジック自体の変更、複数エージェントの並行運用、本番相当のトラフィックでの負荷試験。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 最小権限とコスト上限を備えた状態でエージェントを稼働させる (Priority: P1)

運用者は、チケット管理システムを操作するエージェントを、必要最小限の権限・実行回数の上限・コストの上限をあらかじめ備えた状態で稼働させたい。無防備な状態を経験してから安全対策を追加していくのではなく、最初のリリース時点から安全な状態で運用を開始できることを確認したい。

**Why this priority**: 実運用中のAWSアカウント上でエージェントを動かす以上、権限の過大付与やコスト暴走はそれ自体がセキュリティ・金銭上の実害に直結する。他の安全対策(監査、承認)の土台となる最優先の能力。

**Independent Test**: エージェントに許可範囲外の操作(許可されていないチケットAPI呼び出しや他リソースへのアクセス)を試みさせて拒否されることを確認し、続けて実行回数上限・タイムアウト・コストしきい値をそれぞれ超過する状況を作り、いずれの場合もエージェントの新規実行が自動的に停止することを確認するだけで、単独に価値を検証できる。

**Acceptance Scenarios**:

1. **Given** エージェントが特定のチケットAPI呼び出し(状態参照・状態変更)のみを許可された状態で稼働している、**When** エージェントがその許可範囲外の操作を試みる、**Then** その操作は拒否される
2. **Given** エージェントの実行回数上限が設定されている、**When** 1回の実行の中でその上限に達する、**Then** それ以上の処理は自動的に停止される
3. **Given** エージェントの処理にタイムアウトが設定されている、**When** 処理がタイムアウト時間を超える、**Then** その処理は強制的に終了される
4. **Given** AWS上のコストにしきい値が設定されている、**When** 実際のコストがそのしきい値を超過する、**Then** エージェントの新規実行が自動的に停止し、運用者に通知される
5. **Given** エージェントを初めてリリースする時点、**When** リリースが完了する、**Then** 上記の権限制限・実行回数上限・タイムアウト・コスト超過時の自動停止のすべてが、リリースと同時に有効になっている(無防備な状態で稼働する期間が存在しない)

---

### User Story 2 - エージェントの操作履歴を後から追跡する (Priority: P2)

運用者は、エージェントが過去にどのチケットに対して何を行ったかを、後からいつでも確認できるようにしたい。

**Why this priority**: 権限制御・暴走防止によって安全に稼働していることに加えて、実際に何をしたかを検証できて初めて、無人稼働への信頼が成立する。P1の安全な稼働が前提となるためP2とする。

**Independent Test**: エージェントに一定期間チケットを処理させた後、「先週このエージェントが何をしたか」を運用者が過去の記録だけから再現できることを確認するだけで、単独に価値を検証できる。

**Acceptance Scenarios**:

1. **Given** エージェントがチケットの状態を変更した、**When** 運用者がその操作の記録を確認する、**Then** いつ・どのチケットに対して・何を行ったかが記録から分かる
2. **Given** 一定期間(例:過去1週間)分の操作記録が蓄積されている、**When** 運用者が期間を指定して操作履歴を確認する、**Then** その期間内にエージェントが行ったすべての操作が漏れなく確認できる
3. **Given** エージェントの許可範囲外の操作が試みられ拒否された、**When** 運用者がその記録を確認する、**Then** 拒否された試みそのものも記録として残っている

---

### User Story 3 - 重大な操作は人間の承認を必須にする (Priority: P3)

運用者は、チケットを「完了」にするなど取り消しが困難な重大な操作について、エージェントが自動実行するのではなく、人間の承認を経てから実行されるようにしたい。

**Why this priority**: 権限制御・暴走防止(P1)と監査(P2)によって安全に動き、何をしたか検証できる状態が整って初めて、重大操作の可否判断という一段高度な安全対策が意味を持つ。既存の2つの安全対策の上に積み上げる位置づけのためP3とする。

**Independent Test**: エージェントに重大な操作(チケットの完了)が必要な状況を作らせ、承認せずに放置した場合は操作が実行されないこと、承認した場合にのみ操作が実行されることを確認するだけで、単独に価値を検証できる。

**Acceptance Scenarios**:

1. **Given** エージェントが重大な操作(例:チケットを完了状態にすること)が必要と判断した、**When** その操作を実行しようとする、**Then** 操作は即座には実行されず、承認依頼が人間に通知される
2. **Given** 重大な操作の承認依頼が送られている、**When** 人間がその依頼を承認する、**Then** 保留されていた操作が実行される
3. **Given** 重大な操作の承認依頼が送られている、**When** 人間がその依頼を却下する、**Then** 操作は実行されず、チケットは差し戻し状態に置かれる
4. **Given** 承認依頼が送られてから一定時間が経過しても応答がない、**When** その時間を超過する、**Then** 操作は実行されず、承認待ちのまま保留される(タイムアウトによる自動承認は行われない)

---

### Edge Cases

- コスト超過による自動停止中に、既に承認待ちで保留されている重大操作が存在する場合、その承認依頼自体は取り消されず保留され続ける(自動停止は新規実行のみを止める)
- 実行回数上限に達した直後に、既に送信済みの承認依頼が承認された場合、その操作(保留されていたもの)は実行してよいものとして扱う
- 承認者が誰も応答しないまま長時間放置された場合、操作は実行されず保留状態を維持する(安全側に倒す)
- エージェントの許可されていない操作の試行が短時間に連続して発生した場合、その事実が記録に残り、運用者が異常として検知できる

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、エージェントが実行できる操作を、チケットの状態参照および状態変更など業務上必要な範囲のみに制限しなければならない
- **FR-002**: システムは、エージェントによる許可範囲外の操作(チケット管理システム以外のリソースへのアクセスや、許可されていないAPI呼び出し)を拒否しなければならない
- **FR-003**: システムは、エージェントの1回の実行あたりの処理回数に上限を設定し、上限に達した場合はそれ以上の処理を自動的に停止しなければならない
- **FR-004**: システムは、エージェントの各処理に実行時間の上限(タイムアウト)を設定し、超過した処理を強制的に終了しなければならない
- **FR-005**: システムは、事前に設定したコストのしきい値を実際のコストが超過した場合、エージェントの新規実行を自動的に停止しなければならない
- **FR-006**: システムは、コストしきい値の超過によりエージェントの新規実行を停止した場合、運用者に通知しなければならない
- **FR-007**: FR-001〜FR-006の権限制限・実行回数上限・タイムアウト・コスト超過時の自動停止は、エージェントの初回リリースの時点から有効でなければならない
- **FR-008**: システムは、エージェントが実際に行ったすべての操作について、対象チケット・操作内容・実行日時を記録しなければならない
- **FR-009**: システムは、エージェントの許可範囲外の操作が拒否された事実についても記録しなければならない
- **FR-010**: システムは、記録した操作履歴を、任意の期間を指定して後から参照できる手段を運用者に提供しなければならない
- **FR-011**: システムは、チケットを「完了」にする操作など、取り消しが困難な重大な操作をエージェントが自動的に実行することを禁止しなければならない
- **FR-012**: システムは、重大な操作が必要と判断された場合、その実行を保留し、承認依頼を人間に通知しなければならない
- **FR-013**: システムは、承認依頼に対して人間が承認した場合にのみ、保留されていた重大な操作を実行しなければならない
- **FR-014**: システムは、承認依頼が却下された場合、当該操作を実行せず、チケットを差し戻し状態に置かなければならない
- **FR-015**: システムは、承認依頼に対して一定時間内に応答がない場合、操作を実行せず保留状態を維持しなければならない

### Key Entities

- **エージェント実行 (Agent Run)**: エージェントが1回のトリガーに応じて行う処理のまとまり。開始日時・終了日時・処理対象のチケット・処理結果を持つ
- **操作記録 (Operation Log)**: エージェントが実際に行った、または試みて拒否された1件の操作の記録。対象チケットID、操作内容、実行日時、成功・拒否の別を持つ
- **承認依頼 (Approval Request)**: 重大な操作の実行前に人間の判断を仰ぐための依頼。対象チケットID、依頼対象の操作内容、依頼日時、状態(承認待ち・承認済み・却下・タイムアウト)を持つ
- **コストしきい値 (Budget Threshold)**: エージェント運用を自動停止する条件となるコストの上限値

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: エージェントの初回リリース時点から、権限制限・実行回数上限・コスト超過時の自動停止がすべて有効であり、これらの安全対策が後から追加される期間が存在しない
- **SC-002**: エージェントが許可されていない操作を試みた場合、その操作は例外なく拒否され、実際には実行されない
- **SC-003**: コストが設定したしきい値を超過した場合、検知から一定時間以内にエージェントの新規実行が停止する
- **SC-004**: 運用者は、任意の過去の期間について、その期間内にエージェントが行った操作を漏れなく確認できる
- **SC-005**: チケットを完了させるなどの重大な操作は、人間の承認なしには実行されない
- **SC-006**: 承認依頼が却下またはタイムアウトした場合、対象のチケットは常に安全な状態(差し戻し、または操作前の状態)に保たれる

## Assumptions

- エージェントの役割は既存チケットの状況判断・状態変更・エスカレーションであり、新規チケットの作成は行わない前提とする。そのため許可される操作は「参照」と「状態変更」に限定する
- 実行回数上限・タイムアウト・コストしきい値の具体的な数値は運用しながら調整可能な設定値とし、初期値は学習用リポジトリの想定コスト規模に見合う小さい値から始める
- コストしきい値超過による自動停止は、エージェントの新規実行(新しいトリガーの受け付け)を止めることを指し、既に実行中の処理を強制終了する範囲までは含まない
- 重大な操作の承認依頼が却下された場合、対象チケットはPhase 1で定義済みの「差し戻し」状態に遷移させる
- 承認依頼への応答は、通知を受け取った人間であれば誰でも行える前提とし、承認者ごとの認可・権限管理は本フェーズの対象外とする
- 操作履歴の保持期間は、少なくとも「先週の操作」を確認できる程度(数週間〜1か月程度)を最低ラインとする
- 本フェーズは単一のエージェントが単一のチケット管理システムを操作する構成を前提とし、複数エージェントの並行運用は対象外とする
- Phase 1のチケット管理システムの業務ロジックやAPI仕様自体への変更は行わない
- 本番相当のトラフィックを想定した負荷試験は本フェーズの対象外とする
